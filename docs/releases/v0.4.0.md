# Grajek v0.4.0 release candidate

Status: implemented, with native Windows acceptance still blocked by the available
Linux-only environment. This is not a declaration of a fully verified Windows
port. No commit, push, tag, PR or release publication was performed.

## Scope and architecture

Linux and Windows 10/11 x64 MSVC are the targets. The existing GPUI Kit 0.7.3 /
GPUI 0.3.9, Serenity 0.12.5, Songbird 0.6.1, Symphonia 0.5.5 and Rust 2024 stack
is retained. Queue/repeat, playlist import, range seeking, recovery, history,
volume and persistence continue through the existing authoritative controller.

A shared snapshot projects confirmed playback, metadata, position and independent
transport capabilities. Native events enter the existing bounded command channel;
translation occurs at controller consumption. No optimistic OS state, parallel
queue, focused-key capture, extra polling or new local audio player is introduced.
A successful-seek serial preserves discontinuity information across coalesced
snapshot updates. Track IDs distinguish successive plays of the same URL.

Linux registers the MPRIS root and Player interfaces at
/org/mpris/MediaPlayer2 under org.mpris.MediaPlayer2.grajek on the session bus.
Only changed properties are signalled; Position is queried, Seeked follows
confirmed seeks. Missing bus, name collision and disconnect are nonfatal, with
no reconnect storm. Exclusive acquisition is checked explicitly because the
installed zbus builder can successfully queue a competing name request.

Windows uses the actual GPUI HasWindowHandle and desktop
ISystemMediaTransportControlsInterop::GetForWindow. A small local grajek-smtc
crate isolates three documented unsafe WinRT calls. The application still
forbids unsafe code. STA initialization, foreground task ownership, handler
tokens, partial registration cleanup and same-thread apartment teardown are
explicit. Native callbacks hold no UI references and never await Discord work.
Timeline/button availability follows snapshots. Position handlers capture a
track ID per registration; queued delegates from an older track cannot seek a
new one. Unknown duration clears the Windows timeline instead of inventing a
finite end time. No GlobalSystemMediaTransportControls
manager or keyboard hook is used to publish Grajek's session.

## External controls and metadata

Play resumes Paused or starts a pending queue from Ready/Error. Repeated Play
while playing/resolving and empty Play do nothing. Pause is idempotent. MPRIS
also supplies PlayPause. Next and Stop preserve the existing controller behavior;
Stop retains pending tracks. Previous, OpenUri, playback-rate changes and external
volume writes are unsupported. MPRIS's read-only Volume is the applied Discord
bot gain, not computer master volume; use the in-app slider to change it.

MPRIS Seek is relative microseconds; SetPosition validates the track object path.
SMTC accepts absolute timeline requests where the shell exposes them. Controller
identity/capability checks reject stale or unsupported seeks. Title and known
duration are real metadata; artist, album and artwork remain absent. Loading,
failed/disconnected and no-track states never retain an old Playing session or
metadata. A pending seek retains the last confirmed position.

## Windows feasibility and portability

The unmodified baseline was attempted early with x86_64-pc-windows-msvc. Initial
blocking prerequisites were a missing target, locked Windows dependencies, SDK
and lib.exe. After installing the target and cargo-xwin/SDK, the graph compiled.
Cross-building libopus_sys 0.3.3 with clang-cl required disabling its SIMD in the
local CMake cache. Its build script also checks cfg(unix) on the Linux host and
emits m.lib for Windows; a local empty archive satisfies that cross-only link
request (math functions come from the CRT). Neither workaround changes shipped
sources, lock versions or the native MSVC build configuration.

The resulting Windows debug application and all test executables compile/link.
The first optimized cross-build was blocked because pinned gpui-pre-windows
runs shader generation only on a Windows host. It was then completed without
patching the framework: Microsoft's SDK CPP 10.0.26100.9169 x64 FXC and its DLL
were extracted to /tmp and run under isolated Wine. The exact upstream shader
entry points, shader models and /O3 flags generated all 18 compiled shaders and
the ignored OUT_DIR/shaders_bytes.rs. The release executable then linked. No
SDK executable/DLL is included in distribution. Native Windows CI runs GPUI's
normal build script with SDK FXC; a native runner result is still required.
CI was configured, not executed. Debug builds reference source-tree shaders and
are not portable distributions.

HTTP range code uses portable Rust/Tokio/reqwest primitives. Subprocesses invoke
yt-dlp/deno directly with explicit arguments and hide Windows child consoles.
Shell and /proc fixtures were replaced with the Rust test executable. Windows
storage uses LOCALAPPDATA/Grajek/state.json; Linux XDG locations/mode 0700 stay
unchanged. Serialized same-directory temporary writes, fsync and replacement
remain; Windows replacement/locked-file recovery have target-specific tests.
JSON remains compatible with v0.3.2.

Windows .env lookup: LOCALAPPDATA/Grajek/.env, then .env beside grajek.exe, first
existing file, with explicit environment variables taking precedence. Linux's
existing cwd/ancestor dotenv lookup is retained. Tokens are never saved in state
or included in artifacts. Runtime needs no administrator privileges.

## Prerequisites and distribution

See README for setup. Windows needs the Rust MSVC toolchain, Visual Studio 2022
C++ Build Tools, Windows SDK and CMake. Release shader compilation needs fxc.exe
from that SDK (GPUI_FXC_PATH overrides discovery). The debug PE import table
was inspected: it needs VCRUNTIME140.dll (Microsoft x64 Visual C++ v14 runtime)
and the system ICU library icuuc.dll, requiring Windows 10 version 1703 or later.
Actual Windows version/graphics acceptance remains unverified. Runtime uses Direct3D 11,
DirectWrite/DirectComposition and a feature-level 10.1+ graphics driver. Linux
needs a Wayland/X11 session with working Vulkan drivers and the CI-listed native
build packages. Playback on both OSes needs yt-dlp, Deno >=2.3 and matching EJS
scripts on PATH. Grajek does not download executables or install tools; yt-dlp
may retrieve EJS challenge scripts through its documented ejs:npm fallback.

No installer, signing, updater or automatic release publishing is added. Windows
CI saves an unsigned executable plus README and .env.example, never real secrets.

## Independent review

Open Code Review Delegate v1.13.1 ran in a separate delegated default-model
review, using actual OCR preview/rule commands and full workspace diff/context.
Round 1 covered all 29 files, including manually reviewed lock/docs excluded by
OCR defaults: 100% coverage, no skipped files. It independently reran Linux fmt,
strict Clippy and all 207 then-existing tests.

- F1, high, src/native/linux.rs: early clients could cache CanControl=false
  permanently. The reviewer reproduced the stale cache on an isolated bus.
  Fixed CanControl as a constant intrinsic true support flag; per-command
  availability still follows the controller. Added startup/discovery/cache
  regression coverage without emitting the specification-forbidden change signal.
- F2, low, src/native/linux.rs: generated track paths used the reserved /org/mpris
  prefix. Fixed them to /io/github/amokrzycki/grajek/track/t<ID>; SetPosition and
  metadata share the generator and tests assert the application-owned namespace.

Both findings were accepted; none was dismissed. Round 2 independently reran
the actual OCR preview/rule workflow over all 32 changed files, including the
capture artifacts and manually included lock/docs: 100% coverage, zero skipped.
It verified both fixes and the additional Windows per-track delegate/timeline
hardening. Final outcome: **no actionable findings**, with no unresolved critical,
high, medium or low code finding. It independently passed formatting, strict
Clippy, all 208 enabled Linux tests and the locked build. Native Windows runtime,
CI and audible output remained explicit acceptance gaps, not dismissed defects.
The detailed reports were generated at /tmp/grajek-ocr-round-1.md and
/tmp/grajek-ocr-round-2.md; the durable findings/resolutions are recorded here.
